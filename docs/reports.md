# Reports

Downloadable records — PDF, Excel or CSV — for one vehicle or the whole garage, over any
period. Built at `/dashboard/reports`, generated by `POST /api/reports/export`.

## Shape of the feature

```
src/utils/reports/
  report-range.ts      window presets -> a pair of inclusive YYYY-MM-DD bounds
  report-dataset.ts    vehicles + window -> ReportDataset (rows, profiles, summary, series)
  report-charts.ts     series -> SVG geometry (bars, pie arcs, polyline, axis scales)
  report-csv.ts        dataset -> a flat CSV ledger
  report-xlsx.ts       dataset -> an exceljs workbook
  report-format.ts     formats, MIME types, filenames, PDF-safe money
src/components/reports/
  report-document.tsx    the PDF, and renderReportPdf
  report-charts-pdf.tsx  the charts, drawn from report-charts geometry
  report-theme.ts        the validated palette
src/app/api/reports/export/route.ts   auth, fetch, dispatch, download headers
src/app/dashboard/reports/page.tsx    the builder UI
```

## The one rule worth knowing

**Every cost figure in a report is derived from the rows that report emits.** All three
writers walk the same `ReportDataset`; none of them reads the vehicle graph directly. Three
independent readings of "total spent" would be three chances to disagree, and a report whose
cover contradicts its own tables is worthless.

Distance is the deliberate exception: it comes from every odometer reading in the window,
including ones on records the report does not list, because how far the vehicle travelled is a
fact about the window rather than about the sections the owner ticked.

## Decisions that are easy to get wrong

**Windows are strings, never `Date`s.** Log tables store `date` as a bare calendar date.
Parsing those to compare them reintroduces a timezone the data never had, and a fill logged on
the 1st drops out of a window starting on the 1st for anyone west of UTC.

**Efficiency segments are built over full history, then filtered by closing date.** A segment
routinely straddles the start of the window; the fill that sets its odometer baseline sits
outside. Filtering the logs first and computing after reads 40 km/L where the truth is 20.

**CSV escapes formulas; XLSX must not.** A CSV cell starting `=`, `+`, `-`, `@`, tab or CR
executes when opened in Excel, and `notes`, `location`, `charger_network` and `service_type`
are all free text — so those get an apostrophe prefix, and only text cells do, because running
numbers through the guard turns every negative into text. A string written to `.xlsx` is
stored as a shared string that Excel never evaluates, so the same prefix there would show up
as part of the value and corrupt the note. `report-xlsx.test.ts` pins that difference.

**The PDF cannot draw a rupee sign — or an em dash.** The standard 14 PDF fonts carry WinAnsi;
anything outside it falls through to `.notdef` and renders as *nothing*, with no warning.
Currencies whose symbol is not drawable print their ISO code instead — `INR 4,500.00` — see
`getPdfCurrencyLabel`. Everything else the report emits goes through `toPdfText`, which
substitutes dashes, smart quotes, bullets and ellipses. That one matters more than it sounds:
`ui.common.emptyValue` is an em dash, so before it existed every empty cell in every report
rendered blank. Any string reaching a `<Text>` in the PDF should go through it.

**A report never claims one figure across several vehicles.** The summary efficiency card and
the efficiency-over-time line appear only when a single vehicle is in scope; a multi-vehicle
report gets a spend-by-vehicle pie instead. km/L and km/kWh share no axis, and averaging a
hatchback against a scooter describes neither.

**The energy table's shape comes from its rows, not from `powertrain`.** Fuel rows only means
"Fuel" and no record-type column; charge rows only means "Charging" and no efficiency column,
which is a full-tank measure with no per-session meaning. A vehicle mis-typed in the garage
still reads correctly.

**Chart geometry is a tested module because its failures are silent.** An arc sweeping a full
turn ends where it started and SVG draws nothing, so a petrol-only garage would open its
report to a blank circle. A flat series divides by zero. A one-point polyline renders nothing.
None of that throws.

## Known limits

- **Custom-tracker costs are not included.** A report covers fuel, charging, service and
  vehicle details only, so its total is lower than the one on Trends. The Summary sheet and
  the PDF cover both say what the figure counts. The dataset layer already supports an
  `other` category, so adding it is a UI change rather than a rewrite.
- **Very large garages may be truncated by PostgREST row limits.** The export route uses the
  same nested select as `vehicle-store.ts`. Fine for ordinary histories; an owner with
  thousands of logs could silently lose rows, which matters more in a report than on a
  dashboard. Worth moving to per-table paged queries before anyone hits it.
- **Number grouping is pinned to `en-GB`.** Deterministic across deployments, but it means an
  Indian user sees `1,200,000` rather than `12,00,000`.
- **The spend-by-vehicle pie caps at three vehicles plus "Other".** A colour limit, not a
  design preference: the palette validator puts a fourth categorical slot's orange/yellow pair
  at a normal-vision ΔE of 13.7, below the floor of 15 that labelling does not excuse. The
  exact per-vehicle figures are still in the sections below and in the other two formats.
- **"Battery & odometer check-ins" lists check-ins only.** Fill-ups and charges carry their
  own odometer on their own rows. The section used to be called "Odometer readings", which
  made an EV's report look like it had lost data.
- **Non-Latin text still will not render in the PDF.** `toPdfText` covers the characters the
  app itself emits, but a note or nickname written in another script hits the same WinAnsi
  wall and disappears. The real fix is bundling a font with wider coverage, which is a
  deliberate ~400KB the repo does not carry today.
